sched is self-hosted by design — a single daemon + SQLite, or the full Docker stack with
the web UI (shell).

## The daemon image

The official image is built from the **published** `@schedjs/daemon` npm package —
the artifact that passed the test/parity gates — not from monorepo sources:

```dockerfile
# syntax=docker/dockerfile:1.7
FROM node:24-alpine
WORKDIR /app
ENV NODE_ENV=production
RUN echo '{"name":"schedd","private":true,"packageManager":"yarn@4.18.0"}' > package.json \
 && corepack enable \
 && printf 'nodeLinker: node-modules\nnpmMinimalAgeGate: 0\n' > .yarnrc.yml \
 && CI=1 yarn add @schedjs/daemon@0.10.2 \
 && yarn cache clean
ENV PATH="/app/node_modules/.bin:${PATH}"
ENTRYPOINT ["schedd"]
```

We publish `sched-daemon:<version>` to our registry
(`[[dockerRegistry]]`). Internal builds pull `@schedjs/daemon` from a private npm
registry: the token is passed as a **BuildKit secret** (never an
`ARG`/`ENV` — that would land in the image layers and `docker history`) and the
registry is pointed at it for the duration of the install only:

```bash
# private-registry build (public builds omit the secret + registry arg)
docker build \
  --secret id=registry_token,env=NPM_REGISTRY_TOKEN \
  --build-arg NPM_REGISTRY=[[registryUrl]] \
  -t [[dockerRegistry]]/sched-daemon:0.11.0 apps/daemon
```

`npmMinimalAgeGate: 0` — yarn 4.18 quarantines packages whose publish-time
metadata the private registry doesn't serve; the gate is a supply-chain
nicety we can't satisfy against a private registry.

### Storage adapters are composition

A daemon with a non-sqlite storage is a derived image: `FROM` the base and
`yarn add` the adapter — the same `node_modules` the daemon dynamic-imports at
runtime (`--storage <kind>`, [CLI](cli)). A private npm registry needs a token
for `yarn add` — pass it as a **BuildKit secret** (never an `ARG`/`ENV`: that
lands in the image layers and `docker history`):

```dockerfile
# syntax=docker/dockerfile:1.7
FROM [[dockerRegistry]]/sched-daemon:0.11.0
RUN --mount=type=secret,id=registry_token \
    printf 'nodeLinker: node-modules\nnpmMinimalAgeGate: 0\nnpmRegistryServer: "[[registryUrl]]"\nnpmAlwaysAuth: true\nnpmAuthToken: "%s"\n' "$(cat /run/secrets/registry_token)" > .yarnrc.yml \
 && CI=1 yarn add @schedjs/storage-mongo@0.5.0 \
 && rm -f .yarnrc.yml
```

```bash
# build it — the token enters via the secret mount, not a build arg
docker build --secret id=registry_token,env=NPM_REGISTRY_TOKEN -t schedd-mongo .
```

`npmMinimalAgeGate: 0` is required against a private registry (yarn 4.18 quarantines
packages whose publish-time metadata the private registry doesn't serve), and
**pin the adapter version explicitly** — an unpinned `yarn add @schedjs/storage-mongo`
can silently resolve an older version (age-gate window), and an adapter without
`createStorage(env)` breaks `--storage mongo` at runtime (books T2 finding
2026-08-22). Pin: `yarn add @schedjs/storage-mongo@0.5.0`.

```bash
# run it — connstring only in env, never in arguments
docker run --rm -e MONGO_URL=mongodb://user:pass@db.internal:27017/sched \
  schedd-mongo --tasks /app/tasks.json --storage mongo
```

Same pattern for `@schedjs/storage-mysql` (`MYSQL_URL`) and
`@schedjs/storage-postgres` (`PG_URL`). A **custom** adapter is an npm package
(or a path mounted into the image) exporting `createStorage(env): Promise<Storage>`
([BYO contract](storage/custom)):

```dockerfile
FROM [[dockerRegistry]]/sched-daemon:0.11.0
RUN --mount=type=secret,id=registry_token \
    printf '…registry block (see above)…' > .yarnrc.yml \
 && CI=1 yarn add my-org/sched-storage-redis \
 && rm -f .yarnrc.yml
```

```bash
docker run --rm schedd-mongo --tasks /app/tasks.json --storage my-org/sched-storage-redis
```

If the adapter package is missing from the image, the daemon fails fast with
the exact fix (`RUN yarn add @schedjs/storage-mongo`).

> **Windows (git-bash) operators**: docker run with POSIX-style container paths
> mangles `/app/…` and `/data/…` into `C:/Program Files/Git/…` (→ `unable to
> open database file`). Prefix the command with `MSYS_NO_PATHCONV=1` (or use
> PowerShell / cmd).

## Docker stack (dev)

`docker-compose.dev.yml` at the repo root runs two services:

| Service | Image | Ports | Notes |
|---|---|---|---|
| `daemon` | built from `apps/daemon/Dockerfile` (npm-based, `--storage` ready) | 8080 | `--admin-host 0.0.0.0`, `SCHED_ADMIN_KEY=dev-key`, healthcheck with Bearer, SQLite in a volume |
| `shell` | built from `packages/ui/Dockerfile.serve` | 8095 → 8081 | `sched-ui serve`: static UI + proxies `/api` → daemon |

```bash
docker compose -f docker-compose.dev.yml up --build
```

Web UI: http://127.0.0.1:8095 (shell) · Admin API: http://127.0.0.1:8080 (daemon).

## Security model

Auth lives **at the boundaries** — a private network is not authorization:

- **Admin API / UI** — `SCHED_ADMIN_KEY` (Bearer). In production the daemon binds
  `127.0.0.1`/private network, and a reverse proxy (traefik) terminates TLS.
- **Docker runner** — image allowlist (exact + `prefix*`, fail-fast before spawn) and a
  read-only docker-socket proxy (`POST=0`) instead of a raw socket.
- **HTTP runner** — outbound `x-sched-api-key` per task (see
  [HTTP runner](runners/http)).

## Production deployment (VDS)

Recommended layout behind traefik:

```
traefik ── basicAuth / forwardAuth ──▶ shell (static UI) + /api
                                         │
daemon ── listens 127.0.0.1 / private ──┘  (SCHED_ADMIN_KEY = second layer)
docker runner ──▶ docker-socket proxy (tecnativa, POST=0) + image allowlist
```

- Terminate TLS at traefik; protect the shell + `/api` with basicAuth (or forwardAuth),
  `SCHED_ADMIN_KEY` adds a second layer.
- The daemon never listens on a public interface.
- Deployment artifacts go through the standard admin flow (Portainer, traefik labels).

## Pausing the queue

A running daemon can be frozen with one action and released later — no restart,
no dead `tasks.json` sync, no dead retention. The freeze is **runtime state, not
data**: it is deliberately not persisted, so a restart always comes back in the
state the operator asked for at boot.

Start frozen — boot ordering (DB migrations, worker deploy) where a startup
catch-up burst would hit a half-ready world:

```bash
docker run -e SCHED_START_PAUSED=1 ... schedd --tasks tasks.json
```

`SCHED_START_PAUSED=1` sets the *initial* state only. Release the queue through
the control plane (`engine.resume()` embedded; the admin API / CLI surface ships
with the same wave). There is intentionally no `--start-paused` CLI flag: the
env is the one flag, and compose / Portainer can pass it where a flag cannot be
appended. With the env unset the daemon starts active, exactly as before.

While paused the engine **claims nothing new**. Everything that is not a claim
keeps running: `tasks.json` sync, retention/prune, the async poll loop and
alerts for runs already in flight — a pause is a queue brake, not `docker stop`.

**One caveat: the freeze is per daemon process.** The flag lives in the engine,
not in storage, so with two daemons pointed at the same database
`POST /queue/pause` freezes only the daemon that served the request while its
sibling keeps claiming. Several daemons against one database is not a supported
topology today (the SQL adapters assume a single writer and their migrations are
not lock-guarded); if it becomes one, the pause flag has to move into storage.

### Why pause = skip, not catch-up

On release, a recurring schedule (`cron` / `interval`) whose slot came due while
paused is **skipped**: `nextRunAt` moves to the next future slot via the ordinary
next-slot calculation, and no `missed-slot` fires for the paused window (the slot
was dropped on purpose, not lost). Overdue one-shots (`once`, a deferred `at`)
and pending retries are **kept and played exactly once** — they carry an operator
intent, and silently dropping them loses work.

Catch-up was rejected on purpose. Pause overnight and catch-up means every
schedule fires at once in the morning, each one reported as a `missed-slot`,
against whatever concurrency the box has — the classic thundering herd, plus an
alert storm caused by the operator. "Pause = turn the daemon off" was rejected
too: `tasks.json` sync, retention and in-flight alerts would die with it, and a
pause would be indistinguishable from `docker stop`. Skip semantics is the honest
contract: **missed slots are missed**. To run one on demand, trigger the task by
hand (`sched trigger <task>`).

## Status alerts

sched can push a notification when a run reaches a **terminal state** — failed by
(default) — or when a **schedule slot fired late** (missed-slot, see below). The
channel is a single **universal outbound webhook** (HTTP `POST` + JSON): the
de-facto standard every external world speaks — Slack / Discord / Teams / Telegram /
ntfy / PagerDuty are all POSTs with different JSON, so one endpoint covers them all.
This is the platform-level signal *that* something finished (and how); content
emails and artifact generation stay with the runner
([who generates what](runs#artifacts-who-generates-what)).

Configure it two ways — the daemon accepts an `alerts` option in its
`createDaemon` options, **or** (binary workflow, no code) a top-level `alerts`
block in `tasks.json` (`schedd --tasks tasks.json` picks it up like it picks up
`runners`). A programmatic `alerts` option overrides the file block:

```ts
createDaemon({
  tasksPath: 'tasks.json',
  dbPath: 'sched.db',
  alerts: {
    on: ['failed'],   // default — alert on failures only (also: 'succeeded', 'cancelled')
    onMissed: true,   // default — alert on late schedule slots too; set false to silence
    onSyncFailed: true, // default — alert when the tasks.json sync fails (see below); set false to silence
    onStreak: 3,      // optional — alert once per 3-failure streak instead of every failure (default 1 = today's behaviour)
    webhook: {
      url: 'https://hooks.example.com/sched',
      secret: 'whsec_…',              // optional — enables HMAC signature (see below)
      headers: { 'X-Ops-Token': '…' }, // optional — extra headers for your service
      timeoutMs: 10_000,               // optional — per-attempt timeout, default 10s
    },
    tasks: {                          // optional — per-task routing overrides
      'generate-thumbnail': { on: [] },      // silence a cosmetic task
      'sync-payments': { webhook: { url: 'https://hooks.example.com/pagerduty' } }, // different channel
    },
  },
  missedSlotGraceMs: 120_000, // optional — how late a dispatch must be to count as missed (default 2 min)
});
```

**Sync health — `sync.failed`.** The daemon re-reads `tasks.json` on the sync
interval and reconciles. When that sync fails (storage unreachable — a dead
mongo pool means **nothing** schedules, so a `run.failed` alert could never
fire; or a broken file), the daemon POSTs `sync.failed` to the webhook. Payload:

```json
{ "version": 1, "event": "sync.failed", "error": "…", "consecutiveFailures": 1 }
```

Only the **first failure of a streak** fires (dedupe) — a storage that stays
down for a day does not spam one alert per 60s sync tick. When a sync succeeds,
the streak resets and the next incident alerts again.

**Streak — one alert per incident.** `onStreak` (default `1`) is the number of
*consecutive persistent failures* that makes a task an incident worth a message
(a failure with a retry still scheduled is not counted on its own — the whole
retry ladder is one incident; its depth shows up as `run.attempt`):

- `onStreak: 1` → **no gate**: every terminal failure alerts — the behaviour
every deployment had before this option existed, so an upgrade that changes
nothing in config changes nothing in the inbox.
- `onStreak: N > 1` → the failure alert fires **exactly once per streak**, when
the N-th consecutive failure lands. Failures 2..N stay silent, and so does the
rest of the streak (no reminders — `consecutiveFailures` is in the payload, and
the `FAILS` column in `sched tasks` shows how many failures the task has
accumulated: the task row plus its schedule rows, since a schedule-fired run
advances the schedule, not the task. It is **not** the streak itself — the
streak lives in the engine process, below). A success breaks the streak: the
next incident alerts again.
- **«Отпустило» (recovery)** — the success that broke a streak which had reached
the threshold carries `previousFailures` (how many failures it ended). It is a
`run.succeeded` alert like any other, so it is gated by `on`: with the default
`on: ['failed']` no success notification is sent — add `'succeeded'` to receive
the release signal. A success below the threshold stays a plain `run.succeeded`,
and a `cancelled` run neither counts nor breaks a streak.

The streak is counted in the daemon process (the storage `failCount` is
*cumulative* — it never resets on success — and a persisted consecutive-counter
would be a `Storage`-contract change): a restart forgets an in-flight streak, so
the count restarts from 1 and with `onStreak: N > 1` an incident already in
progress does not alert on the next failure — it re-alerts only after another
N−1 terminal failures, with `consecutiveFailures: N` (the post-restart count,
not the true depth). The cost is lateness, never silence: no alert is lost for
good. Per-task override:
one `alerts` block per task, same field (`onStreak` merges field-wise, task
wins). `onSyncFailed` is root-only — sync health is daemon-global, not a per-task
property.

**Per-task routing.** The root `alerts` block is the channel + defaults; a task can
override its own routing with a task-level `alerts` block in `tasks.json` (or the
`tasks` map above for the programmatic path) — field-wise merge, **task wins,
arrays replace**:

```json
{
  "tasks": [
    { "name": "generate-thumbnail", "runner": "internal", "alerts": { "on": [] } },
    { "name": "sync-payments", "runner": "http", "alerts": { "webhook": { "url": "https://hooks.example.com/pagerduty" } } }
  ],
  "alerts": {
    "on": ["failed"],
    "onMissed": true,
    "webhook": { "url": "https://hooks.example.com/sched", "secret": "whsec_…" }
  }
}
```

- `generate-thumbnail` (`on: []`) stays silent on failure — the root `on` does not
  apply to it. A task **without** an `alerts` block keeps the root defaults.
- `sync-payments` keeps the root `on`/`onMissed` but routes to **its own webhook** —
  the multi-channel escape hatch for criticality ≠ channel.
- Malformed task `alerts` fails at load (see [Tasks → Per-task alert routing](tasks#per-task-alert-routing));
  the root `alerts` block is validated by the same rules (`on`/`onMissed`/`onSyncFailed`/`onStreak`/`webhook`,
  plus the per-task `tasks` map it may carry) — a typo like `onStreak: 0` or `onSyncFailed: "yes"` stops the daemon
  at startup instead of silently disabling alerting.

Instead of SQLite you can hand the daemon any storage adapter (see
[Storage](storage)) — pass `storage` and omit `dbPath`:

```ts
const storage = await createMysqlStorage(pool); // or postgres / mongo / custom
createDaemon({ tasksPath: 'tasks.json', storage, alerts: { … } });
```

At the **binary** level the same choice is `--storage` (see
[CLI → Storage selection](cli#storage-selection-storage)) — the daemon
builds the storage from the connstring env, no code.

```ts
const storage = await createMysqlStorage(pool); // or postgres / mongo / custom
createDaemon({ tasksPath: 'tasks.json', storage, alerts: { … } });
```

### Payload

Every POST carries a JSON body with a `version` (starts at 1 — bump-proof your
consumer against evolution) and an `event` discriminator.

Terminal run states — event is `run.<status>` (`run.failed` / `run.succeeded` /
`run.cancelled`):

```json
{
  "version": 1,
  "event": "run.failed",
  "consecutiveFailures": 3,
  "task": { "name": "publish-video", "runner": "http" },
  "run": {
    "id": "9f1c…",
    "status": "failed",
    "attempt": 3,
    "error": "connection refused",
    "startedAt": "2026-08-19T09:00:00.000Z",
    "finishedAt": "2026-08-19T09:00:01.000Z"
  }
}
```

`consecutiveFailures` rides at the top level (next to `event`, like
`sync.failed`) and is present on failure alerts only. The success that ends a
streak which reached `onStreak` carries `previousFailures` instead:

```json
{
  "version": 1,
  "event": "run.succeeded",
  "previousFailures": 3,
  "task": { "name": "publish-video", "runner": "http" },
  "run": { "id": "a41e…", "status": "succeeded", "attempt": 1, "error": null, "startedAt": "2026-08-20T09:00:00.000Z", "finishedAt": "2026-08-20T09:00:02.000Z" }
}
```

Missed slot — a schedule dispatched more than the grace window after its slot
(downtime catch-up, wedged lock):

```json
{
  "version": 1,
  "event": "missed-slot",
  "task": { "name": "publish-video", "runner": "http" },
  "schedule": { "id": "publish-video#0", "scheduledAt": "2026-08-19T09:00:00.000Z", "delayMs": 32400000 }
}
```

### Signature (HMAC)

When `webhook.secret` is set, sched signs the **exact request body** with
HMAC-SHA256 and sends it as `X-Sched-Signature-256`:

```
X-Sched-Signature-256: sha256=<hex>
```

Verify on your side (Node):

```ts
import { createHmac, timingSafeEqual } from 'node:crypto';

function verify(secret: string, body: string, sig: string | undefined): boolean {
  if (!sig?.startsWith('sha256=')) return false;
  const expected = createHmac('sha256', secret).update(body).digest();
  const received = Buffer.from(sig.slice('sha256='.length), 'hex');
  return received.length === expected.length && timingSafeEqual(received, expected);
}
```

No `secret` → the POST is unsigned (plain webhook, e.g. into a chat gateway).

### Delivery semantics
- **Bounded retry, never fails the run flow.** Up to **3 attempts** total with
  backoff `5s / 30s`. Network errors, timeouts and `5xx` are retried; **`4xx` is
  not** (a config error on the sender's side — retrying is pointless, it logs and
  stops). Exhausted → `[alerts]` error log. The run itself is never affected.
- **Persistent failure = the alert point.** A failed run that still has retries
  scheduled does *not* alert — the notification lands only on the final,
  exhausted failure ([Tasks → retry](tasks#retry)). Manual `triggerTask` alerts
  immediately and never auto-retries. With `onStreak: N > 1` that point is the
  N-th consecutive failure (see above); the alert fires once, not once per run.
- **Missed-slot semantics.** A schedule with run history dispatched more than
  `missedSlotGraceMs` (default 2 min) after its slot fires `missed-slot` —
  engine down at the slot / wedged lock / long queue. The signal is
  cause-agnostic: tune the grace up if your engine legitimately queues runs
  longer than that. Freshly created schedules never fire it — a new schedule's
  first slot is always in the future (past slots are never catch-up-dispatched),
  and the check additionally requires run history (`lastRunAt`), so a
  history-less schedule that is ever dispatched late (e.g. a one-shot with `at`
  in the past) is not reported as a miss either. If the daemon itself is down, detection happens on
  restart — an external uptime monitor covers the gap.
- **Embedded / any engine** — same hooks: `onRunFinal: createAlerts(config).handleFinal`
  plus `onEvent: createAlerts(config).handleEvent` (see
  [Logging → terminal events](logging#_2-terminal-events-onrunfinal)).

> CLI/env wiring for alerts is not implemented yet — the surfaces are the
> `createDaemon({ alerts })` option and the `tasks.json` `alerts` block. On
> request it becomes a daemon flag / `SCHED_ALERTS_*` env.

## Storage

SQLite by default (single file, `--db`). MySQL/MariaDB, Postgres and Mongo are
available as storage adapters (shared history across replicas) via `--storage` —
see [CLI → Storage selection](cli#storage-selection-storage) and
[Storage](storage).
