Get a scheduled task firing in a few minutes. There are **three ways to run sched** —
pick by how much setup you want:

| Path | What you get | Setup |
|---|---|---|
| [1. Embedded](#1-embedded-schedule-functions-in-process) | Schedule **functions** inside your app — no daemon, no Docker | SQLite file + a handler map |
| [2. Standalone daemon](#2-standalone-daemon-http-worker--admin-ui) | Own process, HTTP/Docker workers, **admin UI + alerts** | A worker endpoint + `tasks.json` |
| [3. Docker](#3-docker-everything-in-a-container) | The daemon in a container, compose-friendly | `docker compose up` |

Same engine underneath — run history, retries, priority, `onRunFinal` alerts work on
every path.

> **Note:** `@schedjs/*` packages are distributed via a package registry — install
> through any package manager in step [0](#0-installation); building from source is
> covered there too. Every path in this guide works the same way for both.

## 0. Installation

Packages are published to a package registry (private by default; the public npmjs
after the public release). Access is granted with registry credentials. Install
through any package manager:

## 1. Embedded — schedule functions in-process

Smallest scale: your jobs are **functions, not workers**. `@schedjs/core` embeds in your
app — a SQLite file, a handler map, and the engine. No daemon process, no HTTP, no
Docker. Save this as `embed.mjs` (`.mjs`, not `.js` — the package is ESM-only) and
run it:

```js
// embed.mjs — sched as a library (ESM: the package has no CJS build)
import { DatabaseSync } from 'node:sqlite'
import { createEngine, createInternalRunner, createSqliteStorage, syncTasks } from '@schedjs/core'

const storage = createSqliteStorage(new DatabaseSync('sched.db'))

const engine = createEngine({
  storage,
  runner: createInternalRunner({
    handlers: {
      generateThumbnail: async (data, ctx) => {
        ctx.log('rendering thumbnail')
        return { video: data.videoId, thumb: 'thumb.png' }   // → run.result
      },
    },
  }),
  maxConcurrent: 4, // parallel in-process handlers (default: 1)
})

async function main() {
  await syncTasks(storage, [
    {
      name: 'generate-thumbnail',
      runner: 'internal',
      schedules: [{ cron: '0 9 * * *' }],
      config: { handler: 'generateThumbnail', data: { videoId: 'v-42' } },
    },
  ], new Date())

  engine.start() // renders a thumbnail at 09:00 daily
}

main()
```

```bash
node embed.mjs
```

What you get out of the box: run history in SQLite (`storage.listRuns()`),
[retries with backoff](tasks#retry), priority, and `onRunFinal` alerts.

- Handler contract: `(data, ctx) => result` — a throw is a failed run; `ctx.log` /
  `ctx.setProgress` feed the run record. See [Internal runner](runners/internal).
- Run logging & observability: see [Logging](logging).

**Want the admin UI, HTTP workers, or status alerts?** The engine is the same — move
to the standalone daemon ([Path 2](#2-standalone-daemon-http-worker--admin-ui)) and
reuse your `tasks.json`.

## 2. Standalone daemon — HTTP worker + admin UI

The picture to keep in mind: **sched is the scheduler, a worker is anything that answers
HTTP**. sched fires a request at your worker's URL every time the schedule says so; the
worker replies; sched records the run. In this guide the worker is a 15-line Node server
you run locally — swap it for your real service later.

### 2.1 Write a worker

A worker is just an HTTP endpoint. Save this as `worker.js` and run it:

```js
// worker.js — answers /greet and /fail, everything else — 404
const http = require('node:http')

http.createServer((req, res) => {
  res.setHeader('content-type', 'application/json')

  if (req.url === '/greet') {
    // 2xx = succeeded. The body is what sched stores in run.result
    res.end(JSON.stringify({ greeting: 'hello from worker' }))
    return
  }
  if (req.url === '/fail') {
    res.statusCode = 500
    res.end(JSON.stringify({ error: 'boom' }))
    return
  }
  res.statusCode = 404
  res.end(JSON.stringify({ error: 'not found' }))
}).listen(9999, () => console.log('worker on http://127.0.0.1:9999'))
```

```bash
node worker.js
```

Now something really lives at `http://127.0.0.1:9999` — try it:
`curl http://127.0.0.1:9999/greet`.

### 2.2 Write `tasks.json`

```json
{
  "tasks": [
    {
      "name": "greet",
      "label": "Hello world",
      "schedules": [{ "interval": "every 1 minute" }],
      "config": { "url": "http://127.0.0.1:9999/greet", "method": "GET" }
    },
    {
      "name": "failing-task",
      "label": "Shows a failed run",
      "schedules": [{ "interval": "every 2 minutes" }],
      "config": { "url": "http://127.0.0.1:9999/fail", "method": "GET" }
    }
  ]
}
```

Schedule kinds: `{ "cron": "0 9 * * *" }`, `{ "interval": "every 5 minutes" }`,
`{ "once": "tomorrow at noon" }` — see [Tasks](tasks).

### 2.3 Run the daemon

```bash
SCHED_ADMIN_KEY=dev-key schedd \
  --tasks tasks.json \
  --db sched.db \
  --admin-port 8080
```

(from the monorepo, the same command is `node apps/daemon/dist/entry.js` instead of `schedd`)

- The daemon syncs `tasks.json` as desired state, then starts ticking (1s cadence).
- `--admin-port 8080` serves the admin API (`/api/*`) on `127.0.0.1:8080`. Set
  `SCHED_ADMIN_KEY` to require a Bearer token.
- The web UI ships separately: `npx @schedjs/ui` → `sched-ui serve --proxy http://127.0.0.1:8080`
  (four ways to consume it — see [Admin UI](ui)).

### 2.4 Watch it run

Run the UI and open it:

```bash
npx @schedjs/ui serve --proxy http://127.0.0.1:8080   # → http://127.0.0.1:8081
```

You'll see both tasks and their runs:

- `greet` → runs turn **succeeded**, with `result: { greeting: "hello from worker" }`
- `failing-task` → runs turn **failed**, with the captured error

Every run is recorded with status, timestamps, and result — that's the run history.

**Scale up from here:** add [status alerts](self-hosting#status-alerts) (webhook),
the [MCP server](mcp) for agent tooling, or deploy the same daemon as a
[service](self-hosting).

## 3. Docker — everything in a container

No local Node needed — run the daemon in a container. Get the repo first
(you only need a clone — the Dockerfile builds from it):

[[gitclone]]

Then put `worker.js` and `tasks.json` next to this `docker-compose.yml`:

```yaml
# docker-compose.yml
services:
  sched:
    # image: ghcr.io/schedjs/sched   ← once published, drop the build block
    build:
      context: .
      dockerfile: apps/daemon/Dockerfile
    environment:
      SCHED_ADMIN_KEY: dev-key
    ports:
      - "8080:8080"
    volumes:
      - ./tasks.json:/app/tasks.json:ro
      - sched-data:/data
    command:
      - --tasks
      - /app/tasks.json
      - --db
      - /data/sched.db
      - --admin-port
      - "8080"
      - --admin-host
      - 0.0.0.0

volumes:
  sched-data:
```

```bash
docker compose up
# API: http://127.0.0.1:8080/api/health  (token: dev-key)
# UI:  npx @schedjs/ui → sched-ui serve --proxy http://127.0.0.1:8080
```

Your worker stays on the host (`node worker.js`) and sched reaches it at
`http://host.docker.internal:9999/...` — update the task URLs accordingly, or put the
worker in the same compose file as a second service.

For the full stack with the web UI in a separate container (`sched-ui serve` on
`:8095`, proxying `/api` to the daemon), use the repo's `docker-compose.dev.yml`:

```bash
docker compose -f docker-compose.dev.yml up --build
```

See [Self-hosting](self-hosting) for the layout and security notes.
