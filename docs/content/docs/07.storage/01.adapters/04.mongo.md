---
title: Mongo
description: mongodb driver — shared history across replicas, schemaless by design
---

```bash
npm install @schedjs/storage-mongo
```

```ts
import { MongoClient } from 'mongodb';
import { createMongoStorage } from '@schedjs/storage-mongo';

const client = new MongoClient('mongodb://...');
const storage = await createMongoStorage(client.db('sched'));
```

Use when history must be shared (multi-replica, HA behind a queue).

## Known gotchas

- `insertOne` mutates the passed document (`_id` is injected) — clone before reuse.
- Claim is an atomic findOneAndUpdate — the same lock semantics as SQLite.
- Mongo is **schemaless — there is no `sched_schema_version`**: "migrations on
  open" here means index creation (`nextRunAt`, `name` on tasks; `startedAt`,
  `(taskName, startedAt)` on runs), not versioned schema migrations (by design).
  The sort indexes (`name: 1` on `sched_tasks`, `startedAt: -1` on `sched_runs`)
  were added in 0.5.0 — without them the admin endpoints fall over at ~55k runs
  with Mongo's 32MB in-memory-sort cap.
- `createStorage(env)` retries the **initial** connect for up to 30 s
  (`MONGO_RETRY_MS` overrides) before failing — a brief mongo restart does not
  crash-loop the daemon at boot. After the first connect the **adapter** owns
  reconnection (0.5.1): every storage op is wrapped — on a connection-class
  error (`MongoNetworkError`, `MongoNotConnectedError`, server-selection /
  topology-closed) the adapter forces a fresh topology (`client.close()` +
  `client.connect()`, which re-resolves DNS) and retries (bounded, 2). This is
  the prod lesson from books 2026-08-24: the driver's SDAM did **not** rebuild
  the pool after the mongo container was recreated — `connection 6 … closed`
  for hours, tasks not scheduled, silent. Non-connection errors propagate
  unchanged; a genuinely-down mongo still surfaces as a failed op, not an
  infinite hang.
