The daemon serves a small JSON API under `--admin-port` (mount point `/api`). Bearer auth
is required when `SCHED_ADMIN_KEY` is set:

```
Authorization: Bearer <SCHED_ADMIN_KEY>
```

Unauthenticated requests get `401 { "error": "unauthorized" }`. When no key is configured,
the API is open (bind to a private host in that case).

**Exception: `GET /health` is always open** — even with a key configured, the health
probe answers without credentials (compose healthchecks / LB probes carry none, and the
payload has no secrets). Every other route 401s without the key.

> **Machine-readable contract.** An OpenAPI 3.1 spec ships with the server package:
> `@schedjs/admin-api/openapi.json` — generate a client in any language with
> `openapi-generator` / `kiota` / fern. The spec is route-parity-tested against the
> router (every documented path is exercised; a removed route fails the suite).
>
> **Download without running anything:** the same file is served by this docs site at
> [/openapi.json](/openapi.json) (byte-identical to the package spec, guarded by
> `packages/admin-api/test/ts-client-guard.test.ts`).
>
> **Verified flavors:** Python (`openapi-generator` 7.24.0, suite
> 24/24 + smoke 19/19 against a live daemon) and TypeScript (`typescript-axios`,
> compiles clean under `tsc --strict`; pinned spec copies are byte-identical to the
> package one, guarded by `packages/admin-api/test/ts-client-guard.test.ts`). Two
> generator families over one spec — the 3.1 nullable unions
> (`type: [..., "null"]`) map to `string | null` in both.
>
> **Generator-compatible shapes:****
> - Mutations return **wrapped** records — `{ task }`, `{ run }`, `{ schedule }` —
>   singular GETs return the bare record; the spec declares exactly that.
> - `Schedule` is a **flat output schema** (kind + optional cron/timezone/ms/at) —
>   one-shot rules normalize to `{ kind: "once", at }`, intervals to `{ kind: "interval", ms }`.
> - No `const: true` / no oneOf+discriminator — constructs that make `openapi-generator`
>   emit broken models (string-enums for booleans, `actual_instance=None`).
> - `GET /runs/{id}?logFromOffset=N` declares the incremental-chunk shape
>   (`logChunk` + `logTotalLength` alongside the run).
> - Unknown top-level body fields on `POST /schedules` / `PATCH /schedules/{id}`
>   are rejected with 400 (fail-fast) — a silent-ignored `dedupKey` used to create
>   a duplicate schedule.

> **Cache control.** Every JSON response is sent with `Cache-Control: no-store` (and the
> artifact proxy with `no-cache`), so the browser never serves a cached snapshot of a run.
> The standalone UI (`sched-ui serve`) additionally forces `no-cache` on its `/api/*` proxy
> responses. If a browser still shows a stale list, hard-refresh (Ctrl+F5) once.

> The same API is available to embedded apps: `createAdminApi` from `@schedjs/admin-api`
> returns an `AdminApi` whose `handleRequest(req, res)` you can mount at any path
> (see [Admin UI](ui) § Embedded apps).

## Health

```
GET /api/health   → { "ok": true, "uptimeMs": 1234, "version": "0.16.0" }
```

`version` is the daemon's own package version (falls back to `@schedjs/admin-api` for
embedded hosts — pass `version` to `createAdminApi` to override).

```json
{ "ok": true, "uptimeMs": 123456 }
```

## Runs

```
GET /runs?task=greet&status=failed&limit=20&offset=0
```

| Query | Description |
|---|---|
| `task` | filter by task name |
| `status` | filter by status (`queued` / `running` / `succeeded` / `failed` / `cancelled`) |
| `limit`, `offset` | pagination |

```json
{ "runs": [ { "id": "...", "taskName": "greet", "status": "failed", ... } ] }
```

```
GET /runs/:id          → the RunRecord, or 404
GET /runs/:id?logFromOffset=N → { run, logChunk, logTotalLength } (incremental log read)
DELETE /runs/:id       → delete a finished run (404 unknown, 409 while active — cancel first)
POST /runs/:id/retry   → re-run a run (404 if unknown, 409 if its task is gone)
POST /runs/:id/cancel  → cancel an active run (404 unknown, 409 if already finished)
```

`GET /runs/:id?logFromOffset=N` reads the log **incrementally**:
instead of the full `log` snapshot, the response carries `logChunk` (the tail
starting at offset `N`) and `logTotalLength` (the current total), so a UI can
poll for growth while a run is still writing:

```
GET /runs/ab12cd34?logFromOffset=64
→ { "id": "ab12cd34", ..., "log": null,
     "logChunk": "line2\nline3", "logTotalLength": 21 }
```

- Offset `0` → the whole log as a chunk (same content as the full `log`).
- Offset `≥ logTotalLength` → empty `logChunk` (the UI keeps polling).
- Without the parameter the response is unchanged (full `log` included).

### Manual retry

`POST /runs/:id/retry` executes the run again through its runner (like the task
actions below, it does not touch the schedule). The new run: `data` = the
original run's snapshot, `retryOf` = the original id, `trigger = 'manual'`,
`temporary` inherited from the original, `triggeredBy` fresh — who retries now
(null when the body omits it). The original run is left untouched for audit.
Chains are allowed — a retry can itself be retried.

Accepts an optional JSON body to name the retry actor:

```
POST /runs/ab12cd34/retry
Content-Type: application/json
{ "triggeredBy": "boss@books" }
```

- `triggeredBy` — caller-supplied audit identity (string or null; absent/null =
  anonymous). sched does not verify it — caller-declared, audit-grade not
  auth-grade. Malformed / non-object body → `400`.

```
POST /runs/ab12cd34/retry   → 200 { "run": { "id": "ef56…", "retryOf": "ab12cd34", "trigger": "manual", ... } }
```

### Cancel

`POST /runs/:id/cancel` stops an active run — the worker is
really stopped, not just re-labelled:

```
POST /runs/ab12cd34/cancel   → 200 { "run": { "id": "ab12cd34", "status": "cancelled", ... } }
POST /runs/ab12cd34/cancel   → 409 (already succeeded/failed/cancelled)
POST /runs/nope/cancel       → 404
```

- `queued` (async, being polled) → the worker is told to stop first (when the
  accepted envelope advertised a `cancelUrl`, sched POSTs `{ runId }` there — see
  [Runner protocol → Cancel](protocol#cancel)); then dropped from the poll queue,
  finished `cancelled`, schedule advanced, task lock released. A failed cancel
  signal is recorded in the run's error (`cancel signal failed: <reason>`) — the
  worker may still be running.
- `running` (sync, in flight) → the runner is aborted via `hooks.signal`
  (see [Custom runners → hooks.signal](runners/custom#hookssignal-user-cancel));
  the response is sent after the worker actually stopped.
- A terminal run cannot be cancelled (`409`).

`DELETE /runs/:id` refuses an **active** run (`409` — cancel it first); finished
runs delete normally.

## Tasks

```
GET /tasks?limit=&offset=   → { "tasks": [...] } (name ASC, limit capped at 1000)
GET /tasks/:name            → one task, or 404
POST /tasks                 → create/upsert a task, returns { task } (201 created / 200 updated)
```

### Runtime registration — POST /tasks

Creates a task, or **upserts** an existing one (same semantics as `tasks.json` sync —
the body is a full `TaskDefinition`, validated eagerly with the same fail-fast rules):

```
POST /tasks
Content-Type: application/json

{
  "name": "generate-thumbnail",
  "runner": "http",
  "schedules": [{ "cron": "0 9 * * *" }],
  "config": { "url": "http://worker/thumbnails", "method": "POST" }
}

→ 201

{ "task": { "name": "generate-thumbnail", ..., "nextRunAt": "..." } }
```

- No daemon restart needed — the task is live immediately (a second POST with the same
  name updates it in place; schedule change recomputes `nextRunAt` from now).
- Runtime state is preserved on upsert: `paused`, `failCount`, `retryCount`, `disabled`
  and `nextRunAt` (unless the schedule changed) are never reset.
- Validation failures → `400` with the same messages `tasks.json` uses (fail-fast — a
  typo must not become silent failed runs). Malformed / non-object body → `400`.
- `tasks.json` remains the source of truth for *declared* tasks; a task **removed**
  from the file gets **disabled** by the next sync (see
  [Tasks → Sync semantics](tasks#sync-semantics)). Runtime-registered tasks
  (`fileManaged: false`) are **never** disabled by sync — they live until removed
  via `DELETE /tasks/:name`.
- Embedded callers can register without HTTP: `upsertTaskDefinition(storage, def, now)`
  (exported from `@schedjs/core`).

Actions (ad-hoc, do not touch the schedule):

```
POST /tasks/:name/run      → trigger the task now (engine.triggerTask), returns { run }
DELETE /tasks/:name        → remove a task (204), unknown → 404 (runtime tasks live until deleted)
POST /tasks/:name/pause    → pause the task
POST /tasks/:name/resume   → resume the task
```

`triggerTask` executes immediately through the runner and records run history — it works
for paused/disabled tasks too (explicit manual trigger). A manual run updates the task's
`lastRunId`/`lastRunAt` but never touches the schedule (`nextRunAt` stays put).

> The call **blocks until the run finishes** for sync runners — the response is the
> terminal run. For long sync runs use a scheduled interval (or an async runner)
> if you need the HTTP call to return promptly.

`POST /tasks/:name/run` accepts an optional JSON body to pick the run's retention class,
name the caller, and override its parameters (otherwise the run is `temporary: false`,
`triggeredBy: null` with the task's default `config.data`):

```
POST /tasks/:name/run
Content-Type: application/json
{ "temporary": true, "triggeredBy": "boss@books", "data": { "videoId": "v-42" } }
```

- `temporary: true` → short retention class (24h TTL, see [Runs → Retention](runs#retention)).
- `data` → merged over the task's default `config.data` (`{ ...config.data, ...data }`).
  The worker is dispatched with the merged payload — the override reaches the
  run's execution, not just the audit record.
- `triggeredBy` → caller-supplied audit identity (string or null; absent/null =
  anonymous). sched is identity-agnostic — it does not verify the value
  (caller-declared, audit-grade not auth-grade); embedded callers pass it to
  `triggerTask(name, { triggeredBy })` directly.
- Malformed / non-object body → `400`.

> `POST /tasks/:name/schedule` is **removed**: it answers `404` pointing at
> `POST /schedules` below. Imperative schedules are created there — one schedule
> per rule, each with its own data/policy.

## Schedules (schedule-as-entity)

```
POST   /schedules                → create/upsert, { schedule } — 201 created / 200 updated
GET    /schedules?limit=&offset= → { schedules } (id ASC, limit capped at 1000)
GET    /schedules/:id            → ScheduleRecord | 404
DELETE /schedules/:id            → 204 | 404 (remove a schedule; runs keep their history)
POST   /schedules/:id/pause      → { ok } | 404
POST   /schedules/:id/resume     → { ok } | 404
```

A **schedule** is one firing rule of a task with its own `data`/policy — the
entity that replaced the task's single `schedule` field (one task, one
schedule per channel).

### POST /schedules

```
POST /schedules
Content-Type: application/json

{
  "taskName": "sync-channel-stats",
  "schedule": {
    "cron": "0 9 * * *",
    "data": { "channelId": "UC-ada" },
    "externalId": "ada",
    "dedupKey": "channel-ada"
  }
}

→ 201

{
  "schedule": {
    "id": "...uuid...",
    "taskName": "sync-channel-stats",
    "schedule": { "cron": "0 9 * * *" },
    "tz": "UTC",
    "data": { "channelId": "UC-ada" },
    "nextRunAt": "...",
    "fileManaged": false,
    ...
  }
}
```

- Body: `{ taskName, schedule: { cron | interval | once, timezone?, data?, externalId?,
  dedupKey?, retry?, priority? }, tz? }` — the `schedule` object is the same shape as a
  `tasks.json` schedules element. `tz` defaults to the **task's** timezone; an inner
  `timezone` on cron overrides it.
- **`dedupKey` is the idempotent upsert handle**: a second POST with the same key updates
  the existing schedule in place (its id is preserved) and answers `200`; a fresh schedule
  answers `201`. Without a `dedupKey` every POST creates a new schedule.
- Validation is identical to `tasks.json` (fail-fast): unknown task → `404`; a malformed
  schedule, bad tz, invalid policy → `400`.
- Created schedules are **runtime-owned** (`fileManaged: false`) — sync never disables
  them; remove one with `DELETE /schedules/:id`.

### GET /schedules

Returns every schedule as a first-class row: `id/taskName/schedule/tz/data/externalId/
dedupKey/nextRunAt/lastRunAt/lastRunId/failCount/retryCount/priority/retry/paused/disabled`
plus two resolved fields (no N+1 — three reads total):

- `lastRunStatus` — how the schedule's most recent run ended (`null` when it has no run,
or its last run fell out of the recent window; listRuns is recent-first, capped at 1000).
- `effectiveStatus` — the **AND-semantics made visible**: `'paused-task'`
  (the family stop holds), `'paused-schedule'` (only this instance), or `'active'`. The UI
  renders 🔴 for paused-task and 🟡 for paused-schedule, so «снял паузу, а оно молчит»
  never happens.

```json
{
  "schedules": [
    { "id": "channel-ada", "taskName": "sync-channel-stats", "schedule": { "cron": "0 9 * * *" },
      "tz": "UTC", "data": { "channelId": "UC-ada" }, "nextRunAt": "...", "lastRunAt": null,
      "lastRunId": null, "lastRunStatus": null, "failCount": 0, "retryCount": 0,
      "priority": 0, "retry": null, "paused": false, "disabled": false,
      "effectiveStatus": "active" }
  ]
}
```

`GET /schedules/:id` returns the same shape for one schedule (with `effectiveStatus`);
`PATCH /schedules/:id` edits a schedule **in place** (partial merge — only the
fields present in the body change; an explicit `null` clears, an absent field
keeps its current value). `nextRunAt` recomputes from now when the rule or the
effective tz changed; runtime state (lock, fail count, retry count, last run) is
preserved. Body: `{ schedule: { cron | interval | once, timezone?, data?,
externalId?, dedupKey?, retry?, priority? }, tz? }` — same entry shape as
`POST /schedules`, so a rule-only patch like `{ "schedule": { "cron": "0 9 * * *" } }`
updates the rule and leaves `data`/`dedupKey`/`retry` untouched. 404 on unknown
id, 400 on a bad rule/tz.

`DELETE /schedules/:id` removes the schedule but **keeps its runs** — the audit trail
survives. `POST /schedules/:id/pause|resume` toggles only the schedule-level flag
(`pauseTask` remains the family stop).

## Errors

- `404` — unknown resource
- `405` — method not allowed on a route
- `500` — internal error with the message in `{ "error": "..." }`
